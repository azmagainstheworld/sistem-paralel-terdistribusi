## 1. Pendahuluan

### 1.1 Tujuan Simulasi
Simulasi interaktif ini bertujuan untuk memberikan pemahaman praktis tentang dampak berbagai model komunikasi terhadap aliran data dan interaksi dalam sistem terdistribusi. Melalui simulasi ini, pengguna dapat mengamati secara langsung bagaimana model komunikasi yang berbeda mempengaruhi performa sistem, latency, throughput, dan skalabilitas.

### 1.2 Ruang Lingkup
Simulasi mencakup tiga model komunikasi utama:
- Request-Response
- Publish-Subscribe
- Message Passing

Setiap model diimplementasikan dengan komponen sistem yang realistis dan skenario dunia nyata yang relevan.

## 2. Model Komunikasi yang Diimplementasikan

### 2.1 Request-Response Model
**Deskripsi:** Model komunikasi synchronous dimana client mengirim request dan menunggu response dari server.

**Karakteristik:**
- Synchronous communication
- Tight coupling antara client dan server
- Cocok untuk operasi yang memerlukan immediate response

**Skenario Dunia Nyata:** E-commerce application dimana user mencari informasi produk.

**Komponen:**
- Client: Mobile application user
- Server: Product database server
- Queue: Asynchronous request handling

### 2.2 Publish-Subscribe Model
**Deskripsi:** Model komunikasi asynchronous dimana publisher mengirim pesan ke semua subscribers yang telah subscribe.

**Karakteristik:**
- Asynchronous communication
- Loose coupling
- Scalable untuk multiple receivers
- Fire-and-forget approach

**Skenario Dunia Nyata:** IoT sensor network dimana sensor mengirim data ke multiple monitoring systems.

**Komponen:**
- Publisher: IoT sensor device
- Subscribers: Monitoring dashboards (3 subscribers)
- Topic-based routing system

### 2.3 Message Passing Model
**Deskripsi:** Model peer-to-peer dimana node dapat mengirim pesan langsung ke node lain dalam sistem.

**Karakteristik:**
- Decentralized architecture
- Direct node-to-node communication
- Highly scalable
- Complex routing logic

**Skenario Dunia Nyata:** Distributed computing cluster dimana worker nodes berkomunikasi untuk task distribution.

**Komponen:**
- Nodes: Worker processes (4 nodes)
- Direct communication channels
- Decentralized message routing

## 4. Implementasi Logika Interaksi

### 4.1 Request-Response Implementation
```python
def simulate_rr(self):
    while self.running:
        try:
            message, start_time = self.client_queue.get(timeout=1)
            time.sleep(random.uniform(0.2, 0.8))  # Network latency
            latency = time.time() - start_time
            response = f"Response untuk: {message}"
            self.log_message(f"Server merespons: {response}")
            self.metrics["Request-Response"]["count"] += 1
            self.metrics["Request-Response"]["latency"].append(latency)
        except queue.Empty:
            pass
```

**Logika:**
1. Client mengirim request ke queue
2. Server thread mengambil dari queue
3. Simulasi network delay
4. Server generate response
5. Update metrics (count, latency)

### 4.2 Publish-Subscribe Implementation
```python
def simulate_ps(self):
    while self.running:
        try:
            message, start_time = self.publisher_queue.get(timeout=1)
            time.sleep(random.uniform(0.1, 0.5))  # Broadcast delay
            latency = time.time() - start_time
            for i in range(3):
                self.log_message(f"Subscriber {i+1} menerima: {message}")
            self.metrics["Publish-Subscribe"]["count"] += 1
            self.metrics["Publish-Subscribe"]["latency"].append(latency)
        except queue.Empty:
            pass
```

**Logika:**
1. Publisher mengirim message ke queue
2. Thread mengambil message
3. Simulasi broadcast delay
4. Semua subscribers menerima message
5. Update metrics

### 4.3 Message Passing Implementation
```python
def simulate_mp(self):
    while self.running:
        for i, node_queue in enumerate(self.nodes):
            try:
                message, to_node, start_time = node_queue.get(timeout=0.1)
                time.sleep(random.uniform(0.3, 1.0))  # Routing delay
                latency = time.time() - start_time
                self.log_message(f"Node {to_node+1} menerima dari Node {i+1}: {message}")
                self.metrics["Message Passing"]["count"] += 1
                self.metrics["Message Passing"]["latency"].append(latency)
            except queue.Empty:
                pass
```

**Logika:**
1. Node sender mengirim message ke queue target node
2. Thread check semua node queues
3. Simulasi routing delay
4. Target node menerima message
5. Update metrics

```python
def animate_message(self, start_x, start_y, end_x, end_y, message):
    msg_id = self.canvas.create_text(start_x, start_y, text=message, fill="red")
    dx = (end_x - start_x) / 20  # 20 steps animation
    dy = (end_y - start_y) / 20
    def move():
        nonlocal msg_id
        self.canvas.move(msg_id, dx, dy)
        current_pos = self.canvas.coords(msg_id)
        if abs(current_pos[0] - end_x) > abs(dx):
            self.root.after(50, move)  # 50ms delay per step
        else:
            self.canvas.delete(msg_id)  # Remove message when reached destination
    move()
```

**Fitur Animasi:**
- Pesan bergerak smooth dari sender ke receiver
- 20 step animation dengan 50ms delay per step
- Auto-cleanup saat pesan sampai tujuan

## 9. Interpretasi Hasil Simulasi

### 9.1 Latency Analysis
- **Request-Response:** 200-800ms (network round-trip)
- **Publish-Subscribe:** 100-500ms (broadcast delay)
- **Message Passing:** 300-1000ms (routing complexity)

**Interpretasi:** Request-Response memiliki latency paling konsisten untuk single interactions, sementara Message Passing memiliki variasi tertinggi karena routing complexity.

### 9.2 Throughput Analysis
- **Request-Response:** Moderate throughput, limited by synchronous nature
- **Publish-Subscribe:** High throughput untuk broadcast scenarios
- **Message Passing:** Variable throughput tergantung network topology

**Interpretasi:** Publish-Subscribe menunjukkan efisiensi tertinggi untuk one-to-many communication patterns.

### 9.3 Scalability Insights
- **Request-Response:** Scalable untuk client-server, bottleneck pada server capacity
- **Publish-Subscribe:** Highly scalable untuk large number of subscribers
- **Message Passing:** Most scalable untuk peer-to-peer architectures

### 9.4 Reliability Considerations
- **Request-Response:** High reliability untuk critical operations
- **Publish-Subscribe:** Loose coupling, fault-tolerant
- **Message Passing:** Decentralized, resilient terhadap single-point failures

### 10.3 Message Passing (Lines 205-220)
```python
def send_mp_message(self):
    from_node = int(self.mp_from.get().split()[1]) - 1
    to_node = int(self.mp_to.get().split()[1]) - 1
    message = self.mp_message.get()
    if message and from_node != to_node:
        start_time = time.time()
        self.nodes[from_node].put((message, to_node, start_time))
        start_x, start_y = self.node_positions[from_node]
        end_x, end_y = self.node_positions[to_node]
        self.animate_message(start_x, start_y, end_x, end_y, message)
        self.log_message(f"Node {from_node+1} mengirim ke Node {to_node+1}: {message}")
        self.mp_message.delete(0, tk.END)
```

**Sorotan:** Peer-to-peer communication dengan direct node addressing.
